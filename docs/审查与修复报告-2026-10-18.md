## 二、P0 阻断缺陷（已修复）

### P0-1 未配置 LLM 时终审 100% 否决，所有任务必然 FAILED

- **现象**：库内近期任务（如 `t3923f1a6`、`tcceee3e8`）7 个节点全部 `SUCCESS`，但 `review` 反复 `rejected`，自动修订 2 轮后任务被判失败。空库同样如此。
- **根因**：`AnalystReviewAgent.execute` 用 `llm.complete` 拿裁决；`MockLLM` 返回 `【MockLLM】...`，`_extract_json` 解析失败 → 走 `fallback` → 一律 `rejected`。该设计原本为「防止静默放行」，但导致**任何未配置模型的部署（本地/CI/演示）所有分析任务必然失败**，与项目自身「MockLLM 保证本地可跑」的定位冲突。
- **修复**（`backend/app/agents/analyst_review.py`）：识别 `MockLLM` 时改走**确定性终审**——
  - 无可重算数据集 → `rejected`（不核对数字不放行）；
  - 报告关键数字与数据集重算结果不一致/缺失 → `rejected` 并附证据；
  - 全部一致 → `approved`，裁决意见明确标注「确定性校验」。
  真实 LLM 路径保持原语义（解析失败仍诚实 `rejected`）。
- **验证**：E2E 6 个场景全部 `SUCCESS`；新增 `test_execute_with_dataset_and_mockllm_uses_deterministic_review` 等回归用例。

## 三、分析正确性缺陷（已修复）

### C-1 CSV 金额列选错：把「单价」当「销售额」汇总
- **现象**：需求「对比各大区的销售额」在电商 CSV 上产出 `total_单价`，报告写「单价合计 ¥8,989,784.17」。
- **根因**：`SQLAgent._pick_csv_amount` 只认英文金额列名（`sales/amount/...`），中文列完全落空，退化为「首个数值列」= 单价。
- **修复**：新增中文/英文金额列**优先级分组**（实付 > 应付 > 成交额/销售额 > 总价/金额 > 收入/成本 > 单价），并保留「需求点名列优先」。报告措辞与数据集 `value_label` 随之对齐。

### C-2 CSV 维度选错：说「大区」却按「商品类目」拆
- **现象**：需求「对比各大区的销售额」按 `商品类目` 分组（`region` 存在但未被选中）。
- **根因**：`_DIM_ALIASES` 只有「区域/城市/渠道…」，没有口语化的「大区/战区/省份/品牌/支付方式」。
- **修复**：补齐别名映射（大区、战区、省份、品牌、支付方式等），命中需求词即优先选对应维度。

### C-3 「平均单价」被层层相加（SUM 语义错误）
- **现象**：需求「各区域平均单价对比」输出「单价合计」；改为 AVG 后又出现「平均单价分化：¥5.46 vs ¥13,852，相差 2538 倍」。
- **根因**：① 取数只做 SUM；② `report_facts` 对已是均值的 `avg_*` 列再除一次组内计数。
- **修复**：
  - `SQLAgent`：需求含「平均/均值/均价/人均/户均」→ 按组 `AVG`，列名 `avg_<col>`，数据集带 `agg="avg"`；单价类列的计数语义改为「记录数」而非「订单量」。
  - `report_facts`：`agg="avg"` 时组均值不再二次除计数，并新增**按样本量加权的整体均值** `weighted_avg`。
  - `report_scribe`：均值口径下不再输出「合计/占比/头部集中」等不适用措辞，改为「整体均价 + 最高/最低 + 分化倍数」。
  - 指标口径同步：`_build_spec` 按需求点名列 + AVG 生成 `平均单价 / AVG(单价)`，与取数列**保持一致**。

### C-4 指标知识库口径可能与真实表结构冲突（口径幻觉）
- **现象**：电商 CSV 上报告口径写成 `SUM(\`amount\`)`，但该 CSV 没有 `amount` 列（知识库种子的口径）；房源任务还被无关的「分城市销售额」指标误配。
- **修复**：
  - `_formula_columns` 抽取口径公式引用列，列不存在（或平均口径却给 SUM）时**不采用**知识库公式，保留真实列口径，并在报告中输出「口径校验」说明（可审计）。
  - 知识库匹配阈值收紧：泛标签只加 1 分、必须达到 3 分才采用，杜绝泛标签误配。
  - 报告里的公式统一去掉反引号，避免 Markdown 代码跨度被 `SUM(\`amount\`)` 破坏。

### C-5 DQ→FE 分支丢输入、丢数据集语义
- **现象**：质检触发清洗后，下游报告的「指标口径/数据质量」章节可能缺失；清洗后的数据集丢失 `kind/value_label/dim_label`，报告金额符号与维度措辞失真。
- **根因**：`_on_dq_fe` 用 `set_node_inputs(target, [])` **清空全部上游输入**（连指标口径一起丢）；`FeatureEngineerAgent._build` 重建 dataset 时只保留 `columns/rows/row_count`。
- **修复**：只摘除「原始未清洗数据集」这一条引用（新增 `TaskRepo.drop_node_input_asset`）；FE 透传 dataset 全部语义字段，并把上游 `dq`/`metric_spec` 一并透传，保证重接血缘后下游不丢章节。

### C-6 纯计数数据集出现「合计 0.00」与「平均记录数」等自相矛盾措辞
- **根因**：无可聚合数值列时仍生成一列全 0 的 `total_记录数`；报告按金额模板输出合计/平均。
- **修复**：无度量列时只输出「维度 + 记录数」两列；报告识别「计数数据集」后改用「记录数合计 / 记录数占比」，不再输出平均与占比式金额措辞；单分组数据不再输出「头部集中/尾部偏低/分化」等比较性结论。

### C-7 API 数据源结构推断错误导致指标退化为 `COUNT(data)`
- **根因**：`api_test` 对 `{"data":[...]}` 这类信封响应直接取字典 key 当列（得到一列 `data`），而 `api_fetch_records` 会解包记录列表 —— 两处行为不一致，探查/指标拿到假列。
- **修复**：`api_test` 与取数逻辑对齐，先解包 `data/rows/records/items/list/result` 再取首条记录推断字段。E2E 中 API 场景指标已变为 `SUM(销售额)`。

## 四、调度与可靠性缺陷（已修复）

### R-1 READY 孤儿节点导致任务永久卡死
- **根因**：调度器「置 READY → CAS 认领」之间崩溃时，`reclaim_stale_tasks` 只复位 `CLAIMED/RUNNING`，`READY` 节点不会被 `get_ready_nodes`（只消费 PENDING）再驱动，任务永远无法完成。
- **修复**：`TaskRepo._inflight_statuses()` 纳入 `READY`；集成测试新增 READY 孤儿复位断言。

### R-2 节点终态集合漏 BLOCKED
- **修复**：`task_repo._TERMINAL_NODE_STATUS` 补齐 `BLOCKED`，与调度器侧集合一致，避免 `all_nodes_terminal` 等判定误判。

### R-3 Agent 超时配置非法值会关闭兜底
- **修复**：`base._load_config` 对 `timeout_seconds ≤ 0 / 非整数` 回退默认 120s（0/负数会关闭 `asyncio.wait_for`，禁止）。

### R-4 无表结构时错误信息误导
- **修复**：数据源已接入但探查无表结构时，取数 Agent 明确报「上游探查报告不含真实表结构（连接失败或无可分析表）」，不再笼统提示「未接入数据源」。
